Scaling and performance ⚡

Serial and parallel work

Where lecture 21 started

  • Serial: each line finishes before the next one starts
  • Parallel: independent tasks run at the same time on several cores
  • map applies one function to every element of a list
    • Every parallel tool copies that shape
  • A problem is embarrassingly parallel when the tasks share no state and need no result from each other
  • Our calculation() on ten million random numbers qualified
    • A loop carrying a running total does not
  • Four parallel calls never reached a full 4× saving
    • Starting workers and moving results back costs time
def bar(x):
    return x * x

foo = np.array([0, 1, 2, 3, 4, 5])

list(map(bar, foo))
# [0, 1, 4, 9, 16, 25]
  • Before parallelising anything:
    • Are the tasks independent?
    • Is each one heavy enough to pay for starting a worker?
  • If either answer is no, the cores will not help you

joblib and concurrent.futures

When to reach for each one

  • joblib turns a loop into parallel work in two lines
    • n_jobs=-1 uses every core
from joblib import Parallel, delayed

results = Parallel(n_jobs=6)(
    delayed(bar)(x) for x in foo
)
  • sklearn calls joblib internally whenever you set n_jobs=-1
  • concurrent.futures ships with Python, so it works where you cannot install anything. More about it here
  • Pick the tool from the reason the task is slow:
Your task Tool Why
Number crunching ProcessPoolExecutor The processor is busy
Downloading many URLs ThreadPoolExecutor The processor is idle, waiting
sklearn, numeric loops joblib Calls processes for you
Bigger than RAM Dask Chunks the data itself
  • CPU-bound: the processor is the bottleneck
    • You need more processes, each one on its own core
  • I/O-bound: the program spends its time waiting on the network or the disk
    • Many cheap threads can wait at once while the processor stays free
  • Both executors take a function and an iterable, exactly like map

Big O

How the runtime grows with the input

  • Big O: how runtime grows as the input grows
  • n is the input size: elements in the list you pass in
  • O(1) constant, O(n) linear, O(n²) quadratic
    • Doubling the input costs nothing, twice as much, or four times as much
  • With p cores, an O(n) problem becomes O(n/p + overhead)
  • Parallelism divides the constant; the class stays where it is
  • pairwise_sum: a million operations at 1,000, 10 billion at 100,000
  • O(n log n) beats a parallelised O(n²) on any interesting input
# O(n^2): every pair of elements
def pairwise_sum(data):
    n = len(data)
    results = []
    for i in range(n):
        for j in range(n):
            results.append(data[i] + data[j])
    return results
  • Poor candidates for parallelism:
    • Each step needs the answer from the one before it
    • Tasks share a variable, such as a running total or a counter
      • Taking turns eats the speed-up
    • The disk or memory bus is the limit, so extra cores sit idle

Amdahl’s law

The serial share caps your speed-up

  • Every program has a serial share: the setup, the merging of the results, and any step that waits for the one before it
  • The formula is \(\text{speedup} = \dfrac{1}{s + \dfrac{p}{N}}\), with \(s\) the serial fraction, \(p = 1 - s\) the parallel fraction, and \(N\) the number of cores
  • A program that is 90% parallel, on 8 cores:
s = 0.1        p = 0.9        N = 8

1 / (0.1 + 0.9/8)
  = 1 / (0.1 + 0.1125)
  = 1 / 0.2125
  = 4.7x
  • Eight cores give 4.7×, so nearly half the hardware does nothing for you
  • Push \(N\) to infinity and the ceiling is \(1/s\), which is 10× here
  • A 50% serial program never passes 2×, however large the cluster
  • Measure before you scale: %timeit and cProfile tell you what \(s\) actually is
  • Expect this arithmetic in the quiz

The GIL

Why one thread runs Python at a time

  • CPython has a Global Interpreter Lock: one thread runs Python at a time
    • True however many cores you own
  • Threads help while your code waits
    • The lock is released during a download or a disk read
  • Threads do nothing while your code computes
    • The lock keeps the others idle
  • CPU-bound work needs processes: a separate Python, its own lock
  • NumPy and DuckDB release the GIL while their C and C++ code runs
    • Every core used, no processes to manage
  • A free-threaded build is official since Python 3.14 (still not the default)
  • The same loop, two pools:
# CPU-bound: threads share one lock,
# so the wall clock barely moves
with ThreadPoolExecutor(4) as ex:
    list(ex.map(calculation, chunks))

# Processes: four interpreters,
# four locks, four cores
with ProcessPoolExecutor(4) as ex:
    list(ex.map(calculation, chunks))
  • Swap calculation for a download and the threads win
    • Each one releases the lock while it waits
  • Expect a question on which pool fits which task

Dask

Lazy evaluation, and when a cluster is worth it

  • Dask gives you lazy versions of tools you already use
    • Array for NumPy, DataFrame for pandas, delayed for your functions, Distributed for a cluster
  • Lazy: nothing runs until .compute()
    • Until then you are building a task graph
  • The graph lets Dask optimise the plan and keep memory down
  • .persist() computes a result once and holds it in RAM
    • Use it on a small aggregate, never the raw frame
  • joblib parallelises your functions and leaves the data alone
  • Dask chunks the data itself, so a frame can be larger than your RAM
  • The dashboard at localhost:8787 shows the task stream live
  • A cluster pays off when the data does not fit on the machine
    • Or when the graph has real dependencies between tasks
  • When the data fits in memory it costs you
    • Graph building and chunk moving can make Dask slower than pandas
  • Parquet cut our January 2000 data from 182 MB to 86 MB, and sped up the group-by

SQL revision 🦆

The order a query really runs in

How the engine evaluates a query

  • You write SELECT first, but the engine runs it fifth
  • FROM finds the rows, WHERE filters them, GROUP BY forms the groups, HAVING filters the groups, and SELECT computes the output columns
  • This ladder answers most SQL questions in the quiz, including why an aggregate cannot go in WHERE
  • DuckDB lets you reuse a SELECT alias in WHERE
    • PostgreSQL rejects it, so do not rely on it

WHERE and HAVING

Which clause filters what

  • WHERE filters rows before grouping
  • HAVING filters groups afterwards
  • “Which years count?” is a row question, and “Which countries qualify?” is a group question
  • No aggregate belongs in WHERE, because at that point the groups do not exist yet
  • Every column in your SELECT is either in the GROUP BY or inside an aggregate function
  • ORDER BY can name an alias you created in SELECT, which mean_gdp does here
SELECT country,
       ROUND(AVG(value), 0) AS mean_gdp
FROM wdi
WHERE indicator = 'gdp_per_capita'
  AND year >= 2010
GROUP BY country
HAVING AVG(value) > 60000
ORDER BY mean_gdp DESC
LIMIT 5
  • WHERE year >= 2010 drops old rows
  • HAVING AVG(value) > 60000 drops poorer countries
  • Small economies with financial centres win this list
    • Monaco, Liechtenstein and Bermuda all have fewer than 100,000 people

COUNT(*) and COUNT(value)

Counting rows and counting values

  • COUNT(*) counts rows
  • COUNT(value) counts the rows where value is present
  • Subtract one from the other and you have the number of missing values
  • 217 countries have a GDP row for 2020, and only 208 have a number in it
  • AVG, SUM, MIN and MAX all skip missing values silently
    • A mean can hide a column that is half empty
  • primary_enrolment_net has 217 rows in 2020 and no numbers at all, so COUNT(value) is 0 and AVG is NULL
SELECT year,
       COUNT(*) AS n_rows,
       COUNT(value) AS with_value,
       COUNT(*) - COUNT(value) AS missing
FROM wdi
WHERE indicator = 'internet_users_pct'
  AND year IN (1990, 2000, 2020)
GROUP BY year
ORDER BY year
  • Internet use is recorded for 217 countries in each of those years, with 9 numbers missing in 1990, 21 in 2000, and 33 in 2020
  • Coverage gets worse over time
    • Small territories join the panel and never report the series

The three joins

Which rows survive the join

  • INNER JOIN keeps the rows that match on both sides
    • It filters silently, so a row count that falls after a join usually means this
  • LEFT JOIN keeps the left table whole and fills the missing side with NULL
    • That NULL is the join telling you it found no partner
  • FULL OUTER JOIN keeps everything from both sides
  • In lecture 22 the same two tiny tables gave 5, 6 and 7 rows
  • ON says which columns must agree, and the table aliases keep g.iso3 and r.iso3 apart
  • Which table must survive whole, and what should happen to a row with no partner?

Containers and Docker 🐳

Why working code breaks

Where lecture 23 started

  • “It works on my machine”: your code assumes software you never wrote down
  • Dependencies: the external libraries and tools your code needs
  • Dependency management: making sure it still runs next year
  • Libraries change under you
    • print "hello" was valid Python 2
    • The same line is a SyntaxError in Python 3
  • A 2016 Nature survey of 1,576 researchers
    • More than 70% had failed to reproduce someone else’s experiment
    • More than half had failed on one of their own
  • Missing docs and unrecorded dependencies have a technical fix
  • The ladder, from cheap to thorough:
    • Declare your dependencies in one file
    • Put that file in the repository root
    • Manage them with an environment tool
    • Pin them to exact versions
    • Containerise the whole environment
  • Your project sits at the last rung
    • The marker’s machine has Docker and nothing else
  • Lecture 10’s four ingredients: code, data, environment, documentation
  • A container ships the environment with the code inside it

Ways to pin an environment

venv, conda and uv side by side

venv and pip

  • Ships with Python
  • python3 -m venv .venv, then source .venv/bin/activate
  • pip freeze > requirements.txt writes == pins
  • pip install -r requirements.txt reads them back
  • Two packages became seven lines: pip lists your dependencies’ dependencies
  • Freezing inside conda gives name @ file:///... paths that install nowhere else

conda

  • Handles environments and packages together
  • Installs non-Python software: compilers, R, CUDA
  • conda create --name demo python=3.14 numpy
  • environment.yml is the file you commit
  • --from-history writes a file that travels across operating systems
  • You met it in DATASCI 151

uv

  • Written in Rust by Astral, and fast: eight packages resolved in 1.62 seconds
  • uv init, uv add duckdb, uv sync
  • pyproject.toml for humans, uv.lock for exact versions and hashes
  • Both belong in git, and you never edit the lock by hand
  • uv export --format requirements-txt --no-hashes writes the file your Dockerfile wants

Whichever tool you use, you hand in requirements.txt with == pins, in the repository root, because every Dockerfile reads it

  • Commit both files, and never edit the lock by hand
  • uv export --format requirements-txt --no-hashes > requirements.txt writes the file your Dockerfile reads

Image, container, registry

What each word means

  • An image is a read-only template: OS, libraries, code, configuration
    • You build one from a Dockerfile
  • A container is a running instance of an image
    • One image can start many
  • A registry is where images live, such as Docker Hub
    • docker push and docker pull move them
  • A virtual environment isolates Python packages
    • A container also carries system libraries, the interpreter and your tools
  • A VM boots a whole OS
    • A container carries only what the app needs, so it starts in a second
  • Docker Desktop is free for personal use and open source
    • Also for companies under 250 employees and $10M annual revenue
  • The personal plan caps Docker Hub at 100 image pulls per hour
  • Podman, Colima, OrbStack and Rancher Desktop take the same commands
    • Every docker command in lectures 23 and 25 ran through OrbStack

The project Dockerfile

What each block does

# 1. Base image
FROM ubuntu:24.04

# 2. Build-time settings
ENV DEBIAN_FRONTEND=noninteractive
SHELL ["/bin/bash", "-c"]

# 3. System packages
RUN apt-get update && apt-get install -y [...]

# 4. Quarto
RUN ARCH=$(dpkg --print-architecture) && [...]

# 5. Python environment
RUN python3 -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt /project/requirements.txt
RUN pip install --no-cache-dir -r /project/requirements.txt

# 6. Project files
WORKDIR /project
COPY . /project

# 7. Default command
ENV QUARTO_PYTHON=/opt/venv/bin/python
CMD ["bash", "-c", "quarto render report.qmd && [...]"]
  • FROM pins the starting point to a tag
    • latest moves, and a moving base image breaks reproducibility
  • ENV DEBIAN_FRONTEND=noninteractive stops apt asking questions
  • Quarto 1.10.18 arrives as a .deb, with the version written out in full
    • dpkg --print-architecture picks arm64 or amd64
  • Ubuntu protects its own Python, so we build a venv at /opt/venv
    • It goes first on the PATH
  • COPY requirements.txt sits alone above COPY . /project
    • Editing your report then leaves the slow pip install cached
  • Thirteen instructions, seven commented blocks, eight layers
    • The log counts [1/8] to [8/8]

Building and running the image

What the two commands do

docker build -t datasci350-project .

docker run --rm \
  -v "$(pwd)/output:/project/output" \
  datasci350-project
  • docker build reads the Dockerfile and makes the image
  • The first build is slow: apt, Quarto and pip all download and install
  • Edit report text and rebuild: almost instant, from the cached layers
  • Edit requirements.txt and the cache misses at that COPY
    • pip runs again, and so does every step below it
  • .dockerignore keeps .git, caches and outputs out of the build context
  • docker run starts a container from that image
  • --rm deletes the container when it exits
  • -v host:container links a folder on your laptop to one in the container
    • The host path must be absolute, hence $(pwd)
  • Leave the mount out and the render still succeeds
    • Docker deletes the container, and output/report.html with it
    • The most common Docker mistake in the course
  • -p host:container does the same job for ports
    • docker run --rm -p 8888:8888 quay.io/jupyter/scipy-notebook gives JupyterLab on localhost:8888
  • Your project writes a file and serves nothing, so use -v only

Appendix 02: Solution to Exercise 02

duckdb.sql("""
    SELECT country,
           COUNT(value) AS n_years,
           ROUND(AVG(value), 1) AS mean_internet
    FROM wdi
    WHERE indicator = 'internet_users_pct'
      AND year >= 2015
    GROUP BY country
    HAVING COUNT(value) >= 5
       AND AVG(value) > 95
    ORDER BY mean_internet DESC
    LIMIT 5
""")
┌────────────┬─────────┬───────────────┐
│  country   │ n_years │ mean_internet │
│  varchar   │  int64  │    double     │
├────────────┼─────────┼───────────────┤
│ Iceland    │       9 │          98.7 │
│ Bahrain    │       9 │          98.4 │
│ Luxembourg │       9 │          97.9 │
│ Qatar      │       9 │          97.8 │
│ Denmark    │       9 │          97.5 │
└────────────┴─────────┴───────────────┘
  • WHERE keeps rows, and both HAVING conditions test the group
  • COUNT(value) returns 9 for each of these countries, so the panel holds 2015 to 2023
  • COUNT(*) would return 9 for every country in the world, including the ones with no numbers at all
  • Iceland leads at 98.7%, with Bahrain, Luxembourg, Qatar and Denmark behind it
  • ORDER BY names mean_internet, the alias created in SELECT

Appendix 04: Answers to the Dockerfile questions

  1. FROM ubuntu:24.04 pins the base operating system to one Ubuntu release
    • latest moves: it resolved to 24.04 last year and to 26.04 today
    • A base image that moves breaks reproducibility
  2. COPY requirements.txt on its own line gives pip a layer of its own
    • Editing your report leaves that slow pip install cached
  3. ENV PATH="/opt/venv/bin:$PATH" puts the virtual environment first on the PATH
    • python and pip then mean the ones in /opt/venv, and Ubuntu’s own Python stays untouched
  1. Editing report.qmd misses the cache at COPY . /project, and only that step and the CMD run again
    • Editing requirements.txt misses at COPY requirements.txt, so pip and everything below it runs again
  2. Without -v the render succeeds inside the container
    • --rm then deletes the container, and the file goes with it
    • ls output on your laptop says there is no such directory
