Why SQL, why DuckDB 🦆

Why SQL

You describe the answer, the engine finds it

  • SQL is a language for asking questions of tables
  • It is relational: tables have rows and columns, and you can combine them with joins
  • It is declarative: you say what you want, and the engine decides how to compute it
    • No loops or variable assignments, no input/output code
    • The engine can reorder the query, read fewer columns, or use every core
  • SQL is about fifty years old, and data job adverts list it at least as often as Python
  • Dialects differ in the details, but SELECT, WHERE, GROUP BY and JOIN are the same in DuckDB, SQLite, PostgreSQL, BigQuery and Snowflake

DuckDB’s SQL introduction: https://duckdb.org/docs/stable/sql/introduction

Why DuckDB for a revision class

An in-process engine with no setup

  • Zero setup: pip install duckdb, then import duckdb. In contrast with PostgreSQL, we don’t need a server, a database, a user or a password
  • In-process: the database runs inside your Python session, like SQLite (“SQLite for analytics”)
  • Reads files by name: a Parquet or CSV path goes straight in the FROM clause
  • Reads a pandas DataFrame by its variable name too (more on this later)
  • Columnar and parallel underneath, so the same GROUP BY works on 200 million rows
  • Version on my laptop: DuckDB 1.5.5

Source: https://duckdb.org

First queries

What a table is

Rows, columns and one value per cell

  • A table is a grid: every row is one observation, every column is one variable
  • Each column has one type: text (VARCHAR), whole numbers (SMALLINT), decimals (DOUBLE)
  • Every cell holds one value or nothing. Nothing is written NULL (more on this later)
  • Our table is the WDI panel: 217 countries, 8 indicators, 34 years (1990 to 2023)
  • The measurement is always in value. The column indicator says what it measures
  • So almost every query today starts with WHERE indicator = '...', or it mixes dollars with years of life
  • In pandas terms: a table is a DataFrame, a column is a Series, and there is no index

Creating a view

One name for the file

  • A view is a saved query that behaves like a table
  • CREATE OR REPLACE VIEW wdi AS SELECT ... gives that query the name wdi
  • Every later query then says FROM wdi and never repeats the file path
  • A view holds no data: DuckDB re-reads the Parquet file on each query
  • OR REPLACE overwrites an existing view, so the cell is safe to re-run
  • COUNT(DISTINCT country) counts the different values in a column
  • The panel has 59,024 rows, 217 countries and 8 indicators
  • The view lives in this Python session, so a restart means creating it again
duckdb.sql("""
    CREATE OR REPLACE VIEW wdi AS
    SELECT * FROM '../lecture-19/data/wdi_panel.parquet'
""")

duckdb.sql("""
    SELECT COUNT(*) AS n_rows,
           COUNT(DISTINCT country) AS countries,
           COUNT(DISTINCT indicator) AS indicators
    FROM wdi
""")

DESCRIBE and SUMMARIZE

Two commands to run before any query

  • Run both before writing a query, so you know what the columns are called
  • DESCRIBE lists the columns and their types
  • Five columns here: country, iso3 and indicator are VARCHAR, year is SMALLINT, value is DOUBLE
  • VARCHAR is text, so a filter on it needs single quotes
  • SUMMARIZE adds min, max, count and the share of missing values per column
  • Both take a query, so you can point them at any SELECT
  • 11.06% of value is missing, while country and year have no holes
  • A SUMMARIZE result is itself a table, which is why we SELECT from it here
  • The closest pandas pair: df.dtypes and df.describe()

SELECT, aliases, ORDER BY, LIMIT

Picking columns and sorting the result

  • The whole query is a Python string handed to duckdb.sql()
  • SQL keywords are written in upper case by convention, and select works just as well
  • Column names are case-insensitive too, so Country finds country
  • SELECT lists the columns you want, and * means all of them
    • It can also compute a new one, as ROUND(value, 0) does here
  • AS renames a column in the output, and the new name is an alias
  • ORDER BY value DESC sorts high to low, and ASC is the default
  • LIMIT caps the rows returned, the way .head() does in pandas
duckdb.sql("""
    SELECT country, year,
           ROUND(value, 0) AS gdp_pc
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND year = 2020
    ORDER BY value DESC
    LIMIT 5
""")

WHERE with AND, OR and NOT

Filtering rows with WHERE

  • WHERE keeps the rows whose condition is true, which is boolean indexing in pandas
  • The comparison operators are =, <>, <, <=, > and >=
    • One = tests equality, and <> means “not equal”
  • AND needs both sides true, OR needs either one
  • NOT flips a condition: NOT country = 'Japan' would keep only Brazil
  • Text goes in single quotes, and the comparison is case-sensitive in DuckDB
  • The brackets matter, because AND binds tighter than OR
  • Four rows come back: Brazil on 6,818 and 8,435, Japan on 31,779 and 35,363
duckdb.sql("""
    SELECT country, year,
           ROUND(value, 0) AS gdp_pc
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND (year = 2000 OR year = 2020)
      AND (country = 'Brazil' OR country = 'Japan')
    ORDER BY country, year
""")
┌─────────┬───────┬─────────┐
│ country │ year  │ gdp_pc  │
│ varchar │ int16 │ double  │
├─────────┼───────┼─────────┤

│ Brazil  │  2020 │  8435.0 │
│ Japan   │  2000 │ 31779.0 │
│ Japan   │  2020 │ 35363.0 │
└─────────┴───────┴─────────┘

IN and BETWEEN

Shorter ways to write the same conditions

  • IN replaces a chain of OR comparisons on one column
  • The list goes in brackets, with each text value in single quotes
  • country IN ('Brazil', 'China') is the same test as country = 'Brazil' OR country = 'China'
  • BETWEEN includes both ends, so 2018 and 2020 covers 2018, 2019 and 2020
  • The low end goes first: BETWEEN 2020 AND 2018 returns nothing at all
  • pandas writes these two as .isin([...]) and .between(2018, 2020)
  • Six countries over three years give 18 rows, and LIMIT 6 shows the first six
  • The sort is by country, so those six rows are Brazil and China
duckdb.sql("""
    SELECT country, year,
           ROUND(value, 0) AS gdp_pc
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND country IN ('Brazil', 'China', 'Germany',
                      'India', 'Japan', 'United States')
      AND year BETWEEN 2018 AND 2020
    ORDER BY country, year
    LIMIT 6
""")

LIKE and ILIKE

Matching part of a text value

  • LIKE matches part of a text value instead of the whole of it
  • % stands for any run of characters, including none
  • _ stands for exactly one character
  • So 'United%' starts with United, '%States' ends with States, and '%King%' contains King
  • DISTINCT removes duplicate rows: the view holds one row per country, indicator and year
  • Three countries match: United States, United Arab Emirates and United Kingdom
  • LIKE is case-sensitive, so 'united%' returns zero rows
  • ILIKE runs the same test ignoring case, and finds those same three
  • pandas does this with .str.startswith() or .str.contains()
duckdb.sql("""
    SELECT DISTINCT country
    FROM wdi
    WHERE country LIKE 'United%'
""")

The order a query really runs in

How the engine evaluates a query

  • You write SELECT first, but the engine runs it fifth
  • FROM finds the rows, WHERE filters them, GROUP BY forms the groups, HAVING filters groups, then SELECT computes the output
  • ORDER BY sorts what SELECT produced, and LIMIT runs last of all
  • An aggregate cannot go in WHERE: the groups do not exist yet
  • Standard SQL rejects a SELECT alias inside WHERE. DuckDB accepts it, but the alias never exists before SELECT runs
  • pandas makes you write the steps in this same order: df[mask].groupby(...).agg(...)

Aggregating

GROUP BY

One row of output per group

  • An aggregate function reads many rows and returns one number
  • The five you will use most: COUNT how many, SUM the total, AVG the mean, MIN the smallest, MAX the largest
  • Without GROUP BY, the whole filtered table is one group and you get one row
  • GROUP BY country makes six groups, so the result has six rows
  • Every column in SELECT must sit in the GROUP BY or inside an aggregate
    • SELECT country, value ... GROUP BY country is an error: the group holds 14 different values and SQL will not pick one for you
  • n is 14 for every country, because 2010 to 2023 is 14 years. The same move in pandas: .groupby("country").agg(...)
  • Grouping by two columns gives one row per pair: Appendix 04
duckdb.sql("""
    SELECT country,
           COUNT(value) AS n,
           ROUND(AVG(value), 0) AS mean_gdp
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND country IN ('Brazil', 'China', 'Germany',
                      'India', 'Japan', 'United States')
      AND year >= 2010
    GROUP BY country
    ORDER BY mean_gdp DESC
""")

WHERE and HAVING

Filtering before and after grouping

  • WHERE filters rows before grouping. HAVING filters groups after
  • The run order is WHERE → GROUP BY → HAVING → SELECT → ORDER BY
  • Only HAVING can hold an aggregate, because the groups exist by the time it runs
  • “Which years count?” is a row question, so it belongs in WHERE
  • “Which countries qualify?” is a group question, so it belongs in HAVING
  • HAVING AVG(value) > 30000 leaves three countries standing
  • China, Brazil and India drop out on means of 9,017, 8,923 and 1,694
  • ORDER BY can name the alias mean_gdp, because it runs after SELECT
duckdb.sql("""
    SELECT country,
           COUNT(value) AS n,
           ROUND(AVG(value), 0) AS mean_gdp
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND country IN ('Brazil', 'China', 'Germany',
                      'India', 'Japan', 'United States')
      AND year >= 2010
    GROUP BY country
    HAVING AVG(value) > 30000
    ORDER BY mean_gdp DESC
""")

COUNT(*) and COUNT(value)

Counting rows and counting values

  • COUNT(*) counts rows, whatever those rows hold
  • COUNT(value) counts only the rows where value is present
  • The gap between the two is the number of holes in the column
  • AVG, SUM, MIN and MAX skip missing values without warning you
  • The panel holds 217 country rows in every year
  • 25 values are missing in 1990, 18 in 2000 and 9 in 2020
  • Coverage of GDP per capita improves over time
  • The pandas version of the same check: len(df) against df["value"].count()
  • Run this on any column before you trust its mean
duckdb.sql("""
    SELECT year,
           COUNT(*) AS n_rows,
           COUNT(value) AS with_value,
           COUNT(*) - COUNT(value) AS missing
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND year IN (1990, 2000, 2020)
    GROUP BY year
    ORDER BY year
""")

NULLs, CASE and windows

Missing values

Working with NULL

  • A NULL means “unknown”, so it is neither zero nor an empty string
  • Any comparison with NULL gives NULL, and NULL is not true: NULL = NULL never matches
  • Test with IS NULL, and use IS NOT NULL for the rows that do carry a value
  • COALESCE(a, b) returns a, or b when a is NULL
  • Yemen has a 2020 row with no GDP figure, so it comes back as 0 here
  • Filling with 0 is a choice, and a mean over this filled column would be wrong
  • COALESCE fixes a missing value. A missing row needs a LEFT JOIN (joins section)
  • pandas calls the same thing NaN, and .fillna(0) does this job
duckdb.sql("""
    SELECT country,
           ROUND(COALESCE(value, 0), 0) AS gdp_filled
    FROM wdi
    WHERE indicator = 'gdp_per_capita' AND year = 2020
      AND country IN ('Brazil', 'China', 'Germany', 'India',
                      'Japan', 'United States', 'Yemen, Rep.')
    ORDER BY country
""")

CASE

Writing an if-else ladder inside a SELECT

  • CASE writes an if-else ladder inside a SELECT
  • WHEN states a condition and THEN gives the value to use when it holds
  • The tests run top to bottom, and the first true one wins
  • ELSE catches everything left over, and END closes the ladder
  • Without ELSE, an unmatched row gets NULL
  • The thresholds are the World Bank’s income bands: 13,846, 4,466 and 1,136 dollars
  • The IS NULL test comes first on purpose. Lower down, Yemen would fall through to ELSE and be labelled “Low income”
  • The output is a new column you can group by, join on, or export
duckdb.sql("""
    SELECT country, ROUND(value, 0) AS gdp_pc,
        CASE
            WHEN value IS NULL  THEN 'No data'
            WHEN value >= 13846 THEN 'High income'
            WHEN value >= 4466  THEN 'Upper middle'
            WHEN value >= 1136  THEN 'Lower middle'
            ELSE 'Low income'
        END AS income_band
    FROM wdi
    WHERE indicator = 'gdp_per_capita' AND year = 2020
      AND country IN ('Brazil', 'China', 'Germany', 'India',
                      'Japan', 'United States', 'Yemen, Rep.')
    ORDER BY value DESC NULLS LAST
""")

Window functions

A group-level number on every row

  • GROUP BY year would collapse these twelve rows to two
  • A window function keeps every row and adds a group-level number beside it
  • The window is the set of rows the function looks at for the current row
  • OVER turns an ordinary aggregate into a window function
  • PARTITION BY year splits the rows into groups, one window per year
  • Partition is the window word for group, and no row leaves the output
  • year_mean repeats on every row of its year: 20,885 for 2000 and 26,347 for 2020
  • pandas writes this as .groupby("year")["value"].transform("mean")
duckdb.sql("""
    SELECT country, year, ROUND(value, 0) AS gdp_pc,
           ROUND(AVG(value) OVER (PARTITION BY year), 0)
               AS year_mean
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND country IN ('Brazil', 'China', 'Germany',
                      'India', 'Japan', 'United States')
      AND year IN (2000, 2020)
    ORDER BY year, value DESC
""")

Ranking with a window

RANK() needs an ORDER BY inside OVER

  • RANK() numbers the rows by the ORDER BY written inside OVER
  • There are two ORDER BY clauses here: the inner one decides the ranks, the outer one sorts the printed table
  • No PARTITION BY means one window, covering the whole result
  • Ties share a rank and the next rank is skipped, giving 1, 2, 2, 4
  • DENSE_RANK() gives 1, 2, 2, 3 instead, and ROW_NUMBER() never ties
  • The United States ranks 1 on 59,534 and India ranks 6 on 1,807
  • The ranking covers these six countries only, because WHERE runs first
  • Add PARTITION BY year to rank within each year separately
duckdb.sql("""
    SELECT country, ROUND(value, 0) AS gdp_pc,
           RANK() OVER (ORDER BY value DESC) AS rank_2020
    FROM wdi
    WHERE indicator = 'gdp_per_capita'
      AND country IN ('Brazil', 'China', 'Germany',
                      'India', 'Japan', 'United States')
      AND year = 2020
    ORDER BY rank_2020
""")

Joins

Two small tables

Keys, and the two tables we will join

  • A table is a grid with named columns and one type per column
  • CREATE TABLE ... AS SELECT builds one from a query, as gdp2020 is built here
  • CREATE TABLE (col TYPE, ...) declares empty columns, and INSERT INTO ... VALUES adds the rows
  • A table stores its data, so it differs from the wdi view
  • A primary key identifies a row uniquely, with no duplicates and no NULLs: iso3 in regions
  • A foreign key points at another table’s primary key: iso3 in gdp2020, and a join follows that link with ON g.iso3 = r.iso3
  • Six rows on each side, with two mismatches: JPN has a GDP figure and no region, KOR a region and no GDP figure
  • East Asia holds two codes, which matters in the exercise
duckdb.sql("""
    CREATE OR REPLACE TABLE gdp2020 AS
    SELECT country, iso3, ROUND(value, 0) AS gdp_per_capita
    FROM wdi
    WHERE indicator = 'gdp_per_capita' AND year = 2020
      AND iso3 IN ('USA','BRA','CHN','IND','DEU','JPN')
""")

duckdb.sql("""
    CREATE OR REPLACE TABLE regions
        (iso3 VARCHAR PRIMARY KEY, region VARCHAR)
""")

duckdb.sql("""
    INSERT INTO regions VALUES
        ('USA', 'North America'), ('BRA', 'Latin America'),
        ('CHN', 'East Asia'),     ('IND', 'South Asia'),
        ('DEU', 'Europe'),        ('KOR', 'East Asia')
""")

Reading a join

The ON clause and table aliases

  • A JOIN combines two tables into one wider result
  • ON says which columns must agree: iso3 on both sides
  • Rows pair up when their iso3 values match, and each pair becomes one output row
  • AS g and AS r are table aliases, short names for the two tables
  • g.country means “the country column from gdp2020”
  • Prefix every column in SELECT, so DuckDB knows which table it came from
  • The join type goes in front of the word JOIN, and INNER is the default
  • pandas writes the same thing as pd.merge(gdp2020, regions, on="iso3")
  • The next three slides run this query with three join types
SELECT g.country, r.region, g.gdp_per_capita
FROM gdp2020 AS g
INNER JOIN regions AS r ON g.iso3 = r.iso3
ORDER BY g.country

INNER JOIN

Only the rows that match on both sides

  • An INNER JOIN keeps only the codes present in both tables
  • Six rows on the left, six on the right, five rows out
  • Japan drops out: JPN sits in gdp2020 and appears nowhere in regions
  • Korea drops out too: KOR has a region and no 2020 GDP row
  • The five survivors are Brazil, China, Germany, India and the United States
  • An inner join is a silent filter, and nothing warns you about the two lost rows
  • If your row count falls after a join, this is usually why
  • pandas does the same with pd.merge(..., how="inner")
duckdb.sql("""
    SELECT g.country, r.region, g.gdp_per_capita
    FROM gdp2020 AS g
    INNER JOIN regions AS r ON g.iso3 = r.iso3
    ORDER BY g.country
""")

LEFT JOIN

Keeping every row of the left table

  • A LEFT JOIN keeps every row of the left table, matched or not
  • LEFT means the table named in FROM, which is gdp2020 here
  • Six rows now: Japan is back, with NULL in region
  • The NULL means the join found no partner, and Japan’s 35,363 is untouched
  • Korea is still missing, because it exists only in the right table
  • Swap the two tables and you get a different answer, which is what the exercise asks for
  • The join you will reach for most often: add labels without losing rows
  • pandas writes it as pd.merge(..., how="left")
duckdb.sql("""
    SELECT g.country, r.region, g.gdp_per_capita
    FROM gdp2020 AS g
    LEFT JOIN regions AS r ON g.iso3 = r.iso3
    ORDER BY g.country

FULL OUTER JOIN

Every row from both tables survives

  • A FULL OUTER JOIN keeps every row from both tables, with NULLs on the side that had no partner
  • Seven rows: five matched pairs, plus Korea and Japan
  • Korea’s row carries a region and NULL for country and gdp_per_capita
  • Japan’s row carries a country and 35,363, and NULL for both region columns
  • On these two tables: 5 rows from INNER, 6 from LEFT, 7 from FULL OUTER
  • To choose a join, ask which table must survive whole
  • Then ask what should happen to the rows with no partner

The picture uses cut-down tables, so its counts are 3, 4 and 5. Ours give 5, 6 and 7

Querying a DataFrame by name

Your Python variable becomes a SQL table

Summary

What we learned today

The vocabulary, in the order we met it

  • SQL is declarative: you describe the answer and the engine plans the work
  • DuckDB needs one import and reads a Parquet file or a pandas DataFrame by name
  • A view names a query. DESCRIBE and SUMMARIZE show what is in it

One more question to try on your own

Which countries have had the highest life expectancy since 2010?

  1. Create the wdi view over the panel
  2. Keep only the life_expectancy rows
  3. Keep only the years from 2010 onwards
  4. Compute the mean of value for each country
  5. Keep the countries whose mean is above 82
  6. Sort from highest to lowest
  7. Return the top five, rounded to one decimal
duckdb.sql("""
    SELECT country,
           ROUND(AVG(value), 1) AS mean_life_exp
    FROM wdi

    HAVING AVG(value) > 82
    ORDER BY mean_life_exp DESC

Appendix 03: When something goes wrong

Parser Error: syntax error at or near ".."

The file path is not quoted. Put single quotes around it: FROM '../data/f.parquet'.

IO Error: No files found that match the pattern

The path is quoted but wrong. Paths are relative to the folder you launched Python in, so check with os.getcwd().

Binder Error: Referenced column "gdp" not found

The column name is misspelled or does not exist. Run DESCRIBE SELECT * FROM wdi and read the list

Parser Error: syntax error at or near "SELCT"

A keyword is misspelled. DuckDB quotes the offending word back at you, so read the message to the end.

Binder Error on a value you know exists

You wrote WHERE indicator = "gdp_per_capita" with double quotes. Double quotes mean a column name in SQL, single quotes mean text.

Catalog Error: Table with name wdi does not exist

The view lives in the session that created it. Re-run the CREATE VIEW cell after restarting Python

Appendix 04: Grouping by two columns

Every combination that exists in the data

  • Name two columns and you get one row for each pair that appears in the filtered rows
  • Two countries and two indicators give four rows here
  • Combinations with no rows never appear. SQL does not invent empty groups
  • Japan’s mean life expectancy since 2010 is nine years above Brazil’s. Its CO2 per person is almost four times higher
  • Aggregating a mean of yearly means like this weights every year equally. Say so when you report it
duckdb.sql("""
    SELECT country, indicator,
           ROUND(AVG(value), 1) AS mean_value
    FROM wdi
    WHERE year >= 2010
      AND country IN ('Brazil', 'Japan')
      AND indicator IN ('life_expectancy',
                        'co2_per_capita')
    GROUP BY country, indicator
    ORDER BY country, indicator
""")

Appendix 05: Anti-joins and UNION

Finding rows with no partner

  • An anti-join asks which rows on the left have no partner on the right
  • NOT EXISTS runs a small query for each row and keeps the row when it returns nothing
  • Japan is the only such row here, because JPN is missing from regions
  • A join adds columns. UNION stacks rows from two results that have the same columns
  • UNION removes duplicate rows, UNION ALL keeps them and is faster
  • The tagged result has five rows: Germany, Japan and the United States rich, Brazil and India poor
  • China falls in neither band, so it appears in no row at all
duckdb.sql("""
    SELECT g.country, g.iso3
    FROM gdp2020 AS g
    WHERE NOT EXISTS (
        SELECT 1 FROM regions AS r
        WHERE r.iso3 = g.iso3
    )
""")
┌─────────┬─────────┐
│ country │  iso3   │
│ varchar │ varchar │
├─────────┼─────────┤
│ Japan   │ JPN     │
└─────────┴─────────┘
duckdb.sql("""
    SELECT country, 'rich' AS tag FROM gdp2020
    WHERE gdp_per_capita > 30000
    UNION
    SELECT country, 'poor' AS tag FROM gdp2020
    WHERE gdp_per_capita < 10000
    ORDER BY country
""")
┌───────────────┬─────────┐

Appendix 06: When SQL beats a DataFrame

A checklist for each tool

Reach for SQL when:

  • You are joining two or more tables
  • You are filtering and aggregating a file that is larger than your RAM
  • The question is a GROUP BY with a couple of conditions
  • Someone else has to read the query. A colleague who has never seen pandas can still read your SELECT
  • The data already lives in a database

Stay in pandas when:

  • You need row-by-row logic that has no set-based version
  • You are plotting, or feeding a model
  • You want many small inspectable steps, each one a variable you can look at
  • The reshaping is the hard part, as in the pivot in the DuckDB and pandas section
